# Provenance

This project ports the count reconstruction in Sander Land's ctok v1.3.0,
commit `434612e23c9d9d42d1c5eba23c4761d653e0279d`, under its MIT license.
`REFERENCE.json` records source and dependency SHA-256 hashes. The approved
archive hash identifies the tag codeload archive, not the differently named
commit archive. The tag was checked against the pinned commit before use.

Only the newer V48 family is in scope. Vocabulary witnesses originate from
upstream's measurements; their remaining data provenance uncertainty is not
resolved by this port. No separately licensed evaluation corpora are copied.
This library is unofficial and unaffiliated with Anthropic.

## Unicode oracle

The development-only oracle uses the official digest-pinned Python 3.13.17
linux/amd64 image and regex 2026.8.31. Python category, combining class, case
and NFC behavior use Unicode 15.1.0. The regex Alphabetic and Mark properties
use its Unicode 17.0.0 data. This mixed behavior intentionally matches the
pinned upstream environment rather than selecting the host Go Unicode data.

`tools/reference/generate.py` freezes classification, case mappings and
normalization fixtures. `testdata/unicode/manifest.json` records generator
version, generator and formatted Go output hashes. Official Unicode15.1 NFC
conformance rows are frozen separately under the Unicode data license, not an
upstream ctok evaluation corpus. Ordinary consumer tests require no Python or network.

Invalid UTF-8 is replaced before normalization with `strings.ToValidUTF8(text,
"\uFFFD")`: each contiguous run of invalid bytes becomes one replacement rune.
This is the Go input contract; upstream Python's per-surrogate replacement handles
a different input representation. Literal marker noncharacters remain unchanged
through normalization and are escaped during the later stream construction.

## Vocabulary and count-only tiling

The v1 runtime blob `data/v48.bin` is generated from all non-byte groups in
`pieces_v4_7.json` using upstream's parser and build_vocab. There are 15283 source
records, including 468 byte-prefix records and 3 structural specials. Parsed pieces
plus glued contractions expand to 14819 unique runtime pieces, with 2755 non-marker
unit characters. The runtime byte floor includes those units and the 468 prefixes.
No witness records or JSON are loaded at runtime.

Schema: 8-byte `CTOK48\x00\x01` header, 32-byte SHA256 of the remaining payload,
then little-endian uint32 piece/prefix counts, followed by length-prefixed UTF-8
pieces and raw byte prefixes, each sorted and unique within its section. Record
lengths are uint32; runtime counts and indexes use int. The loader checks bounds,
ordering, UTF-8 and checksum before building a compact reverse trie. Shared state
is initialized once; counting scratch belongs to each call. The newline-tail DP
uses a bounded rolling window, not an input-sized newline string.

Blob SHA256: `ab2710ee915f67313f914163fb6a3e4011227935ec3a0f4a2aa2a1f3c5677350`.
Payload SHA256: `632e57815e584666e9f921a8cc10fceae3e36fd46af3f8dfcc80b57f501dbb26`.
Canonical sorted JSON piece-list SHA256:
`f49fb02d8600ebeb28a38f99f31d652d998919b1734280c325599fa185524c4a`.
Source hash is recorded in REFERENCE.json. Regenerate offline with
`python generate.py vocabulary`, mounting only `/out/data` and `/out/testdata`
writable using the same pinned image and read-only `/work` tooling mount.
`testdata/vocabulary.json` records these hashes, group counts, contractions,
seed 931 byte-floor/marked-stream witnesses and tail costs. The marked-stream
witnesses come from upstream stream_norm and min_vocab_tile, independently of
our later stream implementation. Byte floors map internal U+E000 through U+E004
back to literal U+FDD0 through U+FDD4 before pricing, while trie matching retains
the escaped codepoint. Structural floor markers exclude pad, matching upstream.

The pinned vocabulary's newline ladder is 1 through 16, 24 and 32. Therefore 30
trailing newlines cost 0 beyond the frame, while 29 and 31 cost 1. Upstream's engine
docstring describes 28 as free, but that witness is stale for this data file;
the implementation follows the pinned algorithm and oracle, not that docstring.

## Normalization fallback

The x/text v0.42.0 differential found that its stream-safe normalization inserts
U+034F on long nonstarter runs, unlike Python NFC. Its build tags also select
Unicode 15.0 or 17.0 tables depending on the Go toolchain. The approved fallback
vendors its maintained normalization composition implementation with generated
Unicode 15.1 tables generated by x/text's maintained generator from the official
UCD archive. `tools/reference/ucd.json` pins the archive, extracted files and table.
The archive pin is independently recorded by Fedora, not published by Unicode.
Offline network-disabled Docker regeneration reproduces the table SHA-256.
`internal/norm/README.md` describes the generator registry addition and the two
NFC-only table edits. BSD LICENSE, PATENTS and the root UNICODE-LICENSE retain
the applicable notices. Unicode License V3 was already the outbound data license
when Unicode15.1 shipped. The retained notice uses its 2023 copyright line;
the release-era text is archived at
https://web.archive.org/web/20230911222703/https://www.unicode.org/license.txt.
The UCD15.1 ReadMe directs users to Unicode's terms of use, which apply V3 to
Unicode data unless a specific restriction is stated.

The approved patch uses growable compact segment storage and stable CCC counting
sort, with no automatically inserted CGJ. Maintained composition, Hangul and
property-decoding logic are retained. `tools/reference/norm_patch.json` records
patched source hashes. Unicode helpers and exhaustive scalar, scalar-plus-mark,
canonical-decomposition and long-run oracle fixtures pass on Go 1.26.10 and
1.27.3. The 500000-mark cases include repeated acute and alternating reordered
marks. Race tests, vet and CGO-disabled build pass for this substrate.

Initial NFC-only 1 MiB benchmarks on AMD Ryzen 9 7940HS linux/amd64, Go 1.26.10:
ASCII 0.93 ms and no allocations; acute marks 66.9 ms and 10.52 MB allocated;
alternating reordered marks 69.2 ms and 14.68 MB allocated. These are single-run
initial measurements, not full-counter performance claims.
These historical measurements precede the storage optimization below and are
not current full-counter measurements.

## Public counter and offline parity

The public API supports only explicit family V48. CountContent excludes framing;
Count adds six tokens. The stream port preserves maximal class runs, hard-kind
subdivision, Syriac/stray-mark fusion, contractions, literal-marker escapes,
single-space seams and content-final newline pricing. V48 has no frame bow.
The per-call tiling DP now uses a bounded ring of maximum trie depth plus one;
the reviewed whole-input DP remains as a differential test reference. Case
emission avoids per-word allocations, with the previous case implementation
retained in case_reference_test.go as a test oracle. Output capacity counts
runes and per-run marker bounds, not bytes or an assumed twofold expansion.

`internal/testcorpus/corpus.go` version 1, seed 931, defines 250000 authored valid
UTF-8 cases, totaling 32438088 input bytes. The ten evenly weighted pools cover
code, prose, scripts, marks, markers, seams, digits, scalars, whitespace and long
runs, plus 20 fixed cases. Large cases are bounded at 100 KiB. The generator uses
SplitMix64 and explicit atoms, never Go's version-dependent Unicode tables.
The corpus SHA-256 hashes each uint32 little-endian byte length followed by the
raw bytes, so all control characters are preserved:
`7abf5b4b6bb0d0825c77694b3dbf761ec61eeb48e0de33070edf6d3c53c13467`.

`tools/reference/count_corpus.py` calls upstream's public tokenize API for V48
and verifies its six PAD frame tokens on every case. The deterministic gzip
artifact stores uint32 framed/content count pairs, without runtime witnesses or
corpus strings. Its SHA-256 is
`6d11f6503926a2c94e8fa587c0eef98b64fd0a80f734a835e095a78d4fc0fe69`.

## Recorded live evidence

The development validation completed 18 of 18 generation attempts with Claude
Code 2.1.296. Each of `claude-opus-5-5`, `claude-sonnet-5-5` and
`claude-haiku-5-5` used six fixed slots: baseline, code/JSON, Markdown/prose,
multilingual/Unicode, baseline with nine production code-agent tool schemas, and
mixed text with the same schemas. The baseline system text was `Reply only OK.`;
payload bytes were concatenated directly without a separator, and the user text
was `Reply OK.`. Each generation used a fresh nonpersistent process, an empty
working directory and a one-turn limit. The strict usage-credit safety check ran
before each durable attempt reservation. Metadata-only startup and safety checks
sent no user message and did not consume generation attempts.

Library source commit: `7969144b7665d73ae1e20daee102cf1c5e0947a1`.
Steiner evaluator frozen before the first reservation:
`643bfe916d84ed8dc5083044d0d154dc346132f1`.
The persistent attempt ledger SHA-256 is
`804b66c77a1e0b00041833956a20e006eee2967ab55cd487148491a5d4c29ec1`.
Sanitized observations, payload/tool hashes, normalized requests and recomputable
reports live in Steiner's
`internal/provider/testdata/claude_token_estimation/observations.json`.
Private raw CLI streams and the local ledger are not library artifacts.

Prompt occupancy sums per-message input, cache-creation and cache-read tokens once;
cumulative CLI result usage is never used. Both old and candidate predictions use
Steiner's semantic field traversal, not tokenized wire JSON. Text predictions use
`CountContent(base + payload) - CountContent(base)`.

All models passed the unchanged prospective gates: each text category had at most

gates does not establish provider or whole-request exactness. Model-specific Opus
work remains tracked at https://github.com/luispabon/ctok-go/issues/1.

The launcher requested `--thinking disabled` and
`CLAUDE_CODE_MAX_OUTPUT_TOKENS=64`. A control-only initialization experiment proved
startup acceptance, not effective application. Output tokens and observed thinking
blocks are audit fields, not accuracy gates. Existing production isolation flags
disabled configured setting sources, instruction discovery, auto-memory, skills
and unrelated MCP tools; managed policy and CLI framing remain external uncertainty.
Steiner production activation and the versioned release are separate later steps.

## Normalizer storage bounds and resource evidence

The full counter initially exceeded the 24 bytes/input-byte plus 1 MiB allocation
gate on short words and combining runs. A bounded tiling ring, direct case
emission and run-based stream sizing fixed those cases. Expanded nonstarter runs
(U+0344 and U+0F73) then exposed normalization storage costs. The approved
storage-only adaptation pre-measures segment/output extents, allocates the
8-byte main entries once, packs stable-sort scratch into 4-byte entries and
writes to a pre-sized strings.Builder without a final copy. Composition, Hangul,
property decoding and generated tables are unchanged. There is no CGJ insertion,
truncation, relaxed parity or relaxed resource gate. The extra measurement pass
trades CPU for bounded allocations on non-normal input.

On AMD Ryzen 9 7940HS, linux/amd64, Go 1.26.10, unprofiled development runs:

| Input | 1 MiB allocated | 4 MiB allocated | 1 MiB elapsed |
| --- | ---: | ---: | ---: |
| ASCII code | 7708976 B | 30826800 B | 122 ms |
| Mixed Unicode | 3503720 B | 13984032 B | 92 ms |
| Short words | 10486048 B | 41943328 B | 182 ms |
| Alternating combining marks | 11542816 B | 46145936 B | 107 ms |
| U+0344 expansion | 18882848 B | 75506080 B | 201 ms |
| U+0F73 expansion | 16097568 B | 64332064 B | 179 ms |
| Mixed expansion plus forced sort | 23077152 B | 92283168 B | 213 ms |

The last input is almost all U+0344 followed by U+0F73, forcing sorting across
the maximum-density expanded segment. All 24 pathological input families pass
allocation caps at 1 and 4 MiB and slope <=24 B/input-byte. Cold initialization
in a fresh test subprocess measured 10.4 ms, with 1137792 B retained shared heap
after GC (limits 150 ms and 48 MiB). Tests measure bytes, not allocation counts.
Benchmarks cover 1 KiB, 10 KiB, 100 KiB, 1 MiB and 4 MiB. Timings are machine
specific and uninstrumented; race timings are not normal performance claims.
Independent normalizer review found no underestimates across exhaustive scalar
contexts, Hangul, conformance pairs and 300000 random strings; old/new output
matched on 500000 random strings. In-repo tests fail on any measured-capacity
growth, verify packed sort stability and cover long expanding nonstarter runs.
